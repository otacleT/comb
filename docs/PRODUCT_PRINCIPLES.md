# Comb Product Principles

## Comb とは

**曖昧なアイデアを、AI との対話で「決定済みの仕様」へ収束させる、Spec-Driven Development ツール。**

```
tangled ideas → Comb → decided specs
```

Comb は仕様を「生成」する道具ではない。
**レビュー → 質問 → 人の決定 → 仕様の更新** のループを回し、未決事項を減らしていく道具である。

## 解決する問題

AI Coding Agent の進歩で、「明確な仕様 → 実装」は簡単になった。難しいまま残っているのは、その手前の工程である。

- 要求が曖昧なまま、AI がもっともらしい仕様を書いてしまう。
- 要件どうしの矛盾、境界条件（時間・競合・外部イベント・お金）の抜けに気づけない。
- 決定事項と未決事項が混ざり、「なぜそうなったか」が失われる。
- 仕様の変更が、既存の要件や過去の決定を壊していないか確かめられない。

## Comb の独自の価値

1. **指摘ではなく「答えられる質問」を出す。**
   レビューの発見は、必ず質問にして出す。質問には次の4つを付ける。
   - 具体的な事象の流れ
   - 選択肢
   - 推奨
   - 選択肢ごとの仕様変更

   人が1分で判断できる形にする。
2. **決定（Decision）を残す。**
   回答は Decision（ルール・理由・影響する要件）として追記型で記録し、仕様に反映する。
   「なぜ」が仕様と一緒に残る。
3. **規律のあるレビュー観点。**
   一貫性に加えて、**定式化の規律**を観点として持つ。
   - 用語集、要件の正規化、網羅表、前提の台帳、状態×イベント
   - 境界条件（時間・競合・外部イベント・お金）
   - 変更が仕様全体に与える影響
4. **変更を単位にした収束。**
   OpenSpec と同じく change 単位で仕様を変える。
   未決の質問と、最新の内容に追随できていない古いレビューを、CLI が機械的に示す。

## 原則

### 1. 収束ループを最優先する（Loop first）

最初に作り込むのは、意図 → 提案 → レビュー → 質問 → 決定 → 仕様の更新、というループである。
インフラ、契約、ガバナンスを先に作らない。
進捗は、テストの数ではなく、**実際の LLM で体験が成立したか**で測る。

> 根拠：Converge は 11 日で 825 コミット、10 万行を超えたが、コアのループは最後まで通しで動かなかった。

### 2. 人が読める Markdown が正本（Human-readable first）

正本は `comb/specs/` の Markdown である。ユーザーに形式言語を読み書きさせない。
内部モデルや生成物は、すべて正本から派生させる。

### 3. AI は提案し、人が決め、CLI が書き込む（AI proposes, humans decide, CLI writes）

- AI が書いてよいのは、change 配下の提案物（proposal、delta、review、questions）まで。
- 正本の仕様へのマージは、CLI が決定的に行う。
- LLM に正本を直接編集させない。

> 根拠：OpenSpec では、LLM がマージする経路と CLI がマージする経路が食い違う。

### 4. 発見は質問として、決定は記録として

- 曖昧さや矛盾を AI が勝手に解消しない。必ず質問にする。
- 回答は Decision として残す。Decision の変更は上書きせず、新しい Decision で置き換える（superseded）。

### 5. 規律はプロンプトに、ルールは CLI に

- 構造の規則（ID、フォーマット、状態遷移、ゲート）は CLI が持ち、機械的に検査する。
- レビューの観点や書き方の規律は、CLI が配るテンプレートで Skill に渡す。
- 同じ規則をプロンプトに書き写さない。

### 6. 「検証済み」を軽々しく名乗らない（Honest assurance）

v0 のレビューは AI レビューである。
表示は「レビュー済み・未決 n 件」とし、証明を装わない。
将来、形式検証を入れる場合も、「何を証明したか」と「何をモデル化していないか」を必ずセットで示す。

> 根拠：Spike 01 で、モデル化の漏れが誤った「証明済み」を生んだ。

### 7. 形式手法は価値がある場所でだけ、後から（Formal where proven valuable）

形式検証（FSL）は v0 の中核にしない。
4回の spike で、強い LLM レビューに対する発見力の上乗せは確認できず、コストは大きかった。
証明やテスト生成が必要な中核部分に限り、後のマイルストーンで opt-in として評価し直す。

### 8. 軽さを保つ（Simple before powerful）

- OpenSpec 程度の軽さを守る。
- Entity の種類、ファイルの種類、コマンドの数は、実際に必要になるまで増やさない。
- v0 のモデルは Requirement、Change、Question、Decision の4種類。

### 9. Local-first、エージェント非依存

- 仕様はリポジトリにあり、Git で管理する。
- 独自のクラウドや LLM は持たない。
- v0 は Claude Code を対象にする。ただし Skill の配布は差し替え可能な形にしておく。
- テレメトリはデフォルトで送らない。

### 10. 1つの情報に1つの正本（Avoid duplicate truth）

- コードを見れば一意に分かることは、仕様に書かない。
- 将来のドキュメント生成は、正本からの投影とする。手で編集せず、乖離は検査する。
