# Converge の振り返り（Comb 再出発の前提）

> 調査日: 2026-10-04。対象は `otacleT/converge`（同じリポジトリの worktree 43本を含む）と、前身の `otacleT/reqmap`。読み取りのみで調査した。
> ユーザー自身が書いた振り返りや「再出発の理由」のメモは見つからなかったため、ドキュメント、git 履歴、受け入れレポートから再構成している。

## 何だったか

- **期間と規模**：11日間（2026-09-22〜10-02）で 825 コミット、PR 65 本。ピークは1日193コミットで、エージェント主導の開発だった。
- **ピッチ**：「資料や議事録からアプリの仕様を1つの Markdown にまとめ、最新に保つ」。対象は PL・PM。
- **変遷**：

  | 版 | 内容 |
  |---|---|
  | v1 | Tauri＋React のデスクトップアプリ。8種類の Entity を1項目1ファイルで管理し、承認フローを持つ |
  | v1 再設計 | 承認を廃止し、自動適用と個別の取り消しにした。画面は2つ |
  | v2 | 「Requirements Engineering Harness」。1,122行の仕様書で、Entity 11種類、関係18種類、品質ルール54個、操作12個、マイルストーン M0〜M10 を定義。FSL を「内部の意味的 IR」と宣言した |
  | v3 | デスクトップアプリを捨て、MCP サーバー＋Skill のみにした |

- **規模**：Rust のコア約10万行、テスト5.5万行（1,836個）、ドキュメント127本（約2.3万行、うち計画書18本）。ビルド成果物は160GB、ローカルブランチは125本。

## FSL の使われ方

- v1 では「重いわりに使う場面が限られる」として、**明示的に除外**していた。v2/v3 で、新しい証拠なしに方針を覆した。
- 実際の用途は1つの検査（2つの記述の矛盾検出）だけだった。生成した FSL 名は意味のない ASCII 名で、`fslc` 4.7.0 をサブプロセスとして呼んでいた。
- コード1.17万行と、8版を重ねた1,198行のマッピング契約をかけたが、表現できたのは期間・日付・状態だけ。表示カテゴリのような値は `indeterminate` になった。

## 複雑化の原因

1. **動くループより先にインフラを作った。** コア10万行の段階でも「書き込みの経路がまだない」状態だった。必須の10ルールはすべて `not_run`。
2. **テストの数を進捗と見なした。** 1,329件のテストが通っていても、実 LLM での確認は1回だけ。意味の評価はすべて未実施だった。
3. **コアの価値が受け入れで失敗した。** Claude Code で「新しい資料や回答でドキュメントが更新される」が成立しなかった。
   - Codex の非対話モードが確認フォームを拒否した。
   - 同じ LLM の判定が pass と fail の間で揺れた。
   - フォルダが変わるたびに、保留中の計画がすべて古くなった。
4. **ガバナンスがプロダクトより速く育った。**
   - 全ドキュメントに【確定】【提案】【決定待ち】のタグを付けた。
   - 版の履歴、承認ログ、決定ID 22個、Golden ファイルの凍結、PR ごとの独立レビューを導入した。
5. **方針の反転を繰り返した。**
   - 確認あり → 確認なし → 再びレビュー
   - MCP なし → MCP 中心
   - FSL なし → FSL あり
   - デスクトップアプリ → アプリなし
6. **MCP のツール説明が長すぎた。** `converge_organize` の説明は20,770文字あったが、Claude Code は2,048文字で切り詰める。

## 引き継ぐ概念（コードではなく）

1. ユーザーに見せる状態を3つにする：決定済み／要確認／未決。
2. 発言の立場で分類する。決定として書かれたものだけを仕様にし、要望や検討中のものは質問にする。資料にないことは作らない。
3. **引用の照合**：AI が書いた記述には逐語の引用を付け、機械で照合する。一致しなければ質問にする。
4. 変更は見えるようにし、1つずつ取り消せるようにする。
5. **質問は一度に少数**に絞り、選択肢・推奨・理由を付ける。Question と Decision を分け、変更した Decision は上書きせず置き換える。
6. 正本は、ユーザーのフォルダにある Markdown にする。
7. 評価用のシナリオを持つ（S1 → S3 の入力。「承認不要」という要望を決定と誤読しないか、という罠を含む）。
8. **reqmap から**：抜けを見つけるための網羅グリッド（エラー、ライフサイクル、認可、i18n）。FSL は状態×イベント表にだけ使っていた。こちらの方が FSL に合っている。

## Comb で繰り返さないこと

1. 先にループを作る。実 LLM で「資料 → 文書＋質問 → 回答 → 更新」を成立させてから、規範的な仕様や契約を書く。
2. モデルの種類に上限を設ける。実際の文書が必要としたときだけ型を増やす。
3. FSL は任意かつ狭い用途にとどめ、ベースのプロダクトが動いてから使う。汎用の内部 IR にはしない。
4. 提供形態は、実際の利用面で1日 spike してから一度だけ決める。ツールの表面は小さく保ち、説明文は2KB以内にする。
5. 1人の pre-alpha では、プロセスを軽く保つ（短い PRODUCT と追記型の DECISIONS だけ）。記録済みのスコープ判断は、新しい証拠なしに覆さない。
6. 信頼と履歴は単純にする。差分を見せ、ユーザーが承認し、書き込む。履歴と取り消しは Git に任せる。
7. 並行作業を絞り（ブランチは1〜2本）、進捗は実 LLM での体験の成立で測る。
8. 長い AI 対話から生まれた設計を、そのまま仕様として採用しない。自分で確かめた少数の原則に蒸留する。
