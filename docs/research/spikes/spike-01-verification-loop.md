# Spike 01: Formal Verification ループの価値検証

実施日: 2026-10-04 / コードはすべて使い捨て（`.spike/` は git 管理外）

## 問い

現実的な状態遷移を含む仕様で、`Markdown → IR → FSL → 反例 → 質問` のループは、
**Claude単体のレビューが見逃す、回答可能な質問**を見つけられるか？
あわせて、Markdown→IR抽出、IR→FSLコンパイル、反例→質問変換が実用になるかを確かめる。

## 実験設計

偏りを避けるため、各工程を独立したエージェントに分けた（相互の成果物は見せない）。

| 工程 | 担当 | 入力 | 出力 |
|---|---|---|---|
| 仕様作成 | PM役エージェント（検証の存在は知らせない） | 会議メモ風の要求 | `spec/order-lifecycle.md`（624行、REQ 18件、シナリオ52件） |
| ベースライン | レビュアー役エージェント | 仕様のみ | `baseline/review.md`（23件） |
| IR抽出 | 抽出エージェント | 仕様 + `ir/ir-format.md` | `ir/order-lifecycle.ir.yaml` |
| コンパイル + 検証 | 決定的スクリプト（`compiler/`） | IR | `out/findings.json` |
| 質問化 | 質問化エージェント（ベースラインは見せない） | 仕様 + IR + findings | `questions/round1.md` |
| 回答 → 再検証 | 回答はシミュレーション（私が選択） | — | `out-r2/`、`out-r2b/`、`out-enum/` |

- 題材：C2Cマーケットプレイスの注文ライフサイクル。対象は決済、発送、キャンセル、Dispute、返品、返金、チャージバック、出金。
- FSL は 4.8.1 を使った。IR → FSL は requirements 方言の kernel-wrapper 形式に変換した。

## 分かったこと

1. **強いLLMレビューに対して、Verifierの「発見力」の上乗せは小さい。** 少なくとも、よく書かれた仕様を同じ系統の強いモデルが時間をかけてレビューした場合はそうだった。仕様がもっと雑な場合や、モデルが弱い場合は未検証。
2. **Verifierに固有の価値は「発見」ではなく「保証」にある。**
   - 回答を反映した仕様が、全ルールについて全状態で成り立つことを証明できる（ラウンド2）。LLMレビューは、自分が提案した修正が別の箇所を壊さないことを保証できない。
   - 最短の再現手順が出る。
   - デッドロックがないこと、全アクションが到達可能であること、シナリオ40件が再生できることを、機械的に確認できる。
3. **IRの質がすべてを決める。** お金の流れを1つ落としただけで（チャージバックで買い手に戻る額）、二重返金があるのに「証明済み」になった。これは誤った安心感の典型例。
4. **「カバーしていないこと」の開示が、次のIR改善の手がかりになる。** 質問化エージェントは「チャージバックで動くお金は扱っていない」と自ら開示していた。それを変数化したラウンド2bで、BL-06 が検出された。
5. **Markdown → IR の抽出は、それ自体がレビューとして効く。** 構造化を強いることで、6件の問題が抽出時に見つかった。
6. **反例 → 質問 は LLM で十分自動化できる。** 質も高い（円での例示、仕様変更案付きの選択肢、推奨）。難所と、その対策は次の3つ。
   - 根本原因ごとのグルーピング → 対策：トレースの先頭部分と、扱われていない変数でまとめる。
   - 各ステップが仕様上本当に可能かの検証 → 対策：抽出メモと要件IDで紐付ける。
   - ルール自体が強すぎるケースの判別 → 対策：独立した工程にする。
   - findings にも次の改善が要る：各ステップの完全な状態を含める、除外したプロパティを明示する。
7. **FSLは1プロパティにつき反例を1つしか返さない。** 実用には列挙が必要。違反ステップのガードを「そのステップでルールが壊れない条件」で強化して再検索する方法（事後条件の代入）がうまく機能し、5経路を列挙できた。これは質問の選択肢「(i) 最後の手順を禁止する」の具体的な文言にもそのまま使える。
8. **性能について**
   - 違反の発見は1秒未満。
   - 1インスタンスの完全な証明は1分前後。
   - 2インスタンスの明示探索は爆発する。
   - liveness と2インスタンスの BMC は数分かかる。
   - v0 のデフォルトは「1インスタンス・明示探索」とし、2インスタンスと liveness は非同期のオプションにする。
9. **IR形式の表現力ギャップ**（抽出エージェントの報告から、重要な順）
   1. 条件付き効果がない（アクションの重複を招く。強制キャンセルが8つに分かれた）
   2. enum の型共有や snapshot がない
   3. 1アクションで複数インスタンスを扱えない（残高を注文ごとに近似した）
   4. 全インスタンスにまたがる集約ができない
   5. 「P の間は X しない」というルール種別がない
   6. `at_most_once` がアクション集合を取れない
   7. 乗除算がない
   8. 1アクション内で非決定的に値を選べない
   9. 期限の2段階モデル化の規約がない
   10. 代入が事前状態を読むという意味論が明文化されていない
10. **FSL固有の障害はなかった。**
    - コンパイル先として安定していた。
    - JSON は十分な情報を持っていた。
    - `@requirement` で Requirement ID が付き、そのまま返ってきた。
    - 注意点は2つ。scenario の失敗が verify 全体のエラーになるため、ファイルを分ける必要がある。1プロパティ1反例。

## Combへの示唆

- **価値の置き方を修正する。** 「Verifierがバグを見つける」ではなく、次の2段構えにする。
  - **LLMレビューが広く見つける。**
  - **Verifierが本物かどうかを確かめ、修正後の仕様が壊れていないことを証明する。**

  LLMレビュー（explore/propose 時）は Comb の正式な機能として持つ。
- **「Verified」には、必ずカバレッジの開示を添える。** 「何を証明したか」と「何をモデル化していないか」をセットで見せる。開示をIR改善のループに組み込む。
- **IR は Markdown に埋め込まない。** 62アクション規模になり、人が読む表にはならない。IR は要件IDで追跡できる、コミットされる派生物として持つ。人が確認するのは IR そのものではなく、「検証で確認できたこと／カバーしていないこと」と質問。
  - これは前回提案した「仕様Markdown内の構造化セクション」案の修正にあたる。
- **まだ検証していない最大の仮説は「変更時の回帰検出」。** 600行の仕様に変更（delta）が入るたびに、LLMが全体を再レビューして矛盾を拾えるか。それとも Verifier の方が確実か。Comb の change ライフサイクルと最も相性がよく、差別化の本命になりうる。
