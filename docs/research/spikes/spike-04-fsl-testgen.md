# Spike 04（机上調査＋生成の試行）：FSLでテスト作成は楽になるか

実施日: 2026-10-05

## FSLのテスト関連機能（4.8.1）

| コマンド | できること |
|---|---|
| `fslc testgen --target pytest\|vitest\|swift\|kotlin\|dart\|phpunit` | 実装と仕様を照合する適合性テストを生成する。実装側は Adapter（`reset` / `step(action, params)` / `observe()`）を書くだけ。生成されるテストは次の4種類。<br>• cover（アクションごと）<br>• acceptance / forbidden（仕様に書いたトレース）<br>• respond（liveness の例）<br>• 固定シードのランダムウォーク100ステップ（仕様の解釈器が正解。vitest では生成時に焼き込み） |
| `fslc scenarios` | 上記のシナリオを JSON の雛形として出す |
| `fslc testplan` | 適合性ベクトルの選定（test-plan.v1） |
| `fslc replay --trace` / `--from-log --mapping` | 実行ログや本番の JSONL ログを仕様に照らして検査する（実行時の適合性） |
| `fslc conformance` | 言語に依存しない具体的な適合性ベクトル |
| `fslc typestate --ts` | TypeScript の型状態（ghost types）の雛形 |

## 試行結果

| 対象 | 深さ | 時間 | 生成物 |
|---|---|---|---|
| Spike 1/2 の IR モデル（注文1件） | 6 | 7.7秒 | 62テスト（cover 59、respond 2、ランダムウォーク1）、934行 |
| Spike 3 の公式仕様（注文2件） | 4 | **約2時間で異常終了、出力なし** | — |
| 同上、注文1件に変更 | 3 | 即失敗 | 注文2件を前提とする受け入れトレース（同梱発送）が再生できない |
| 同上（注文2件） | 2 | 28.7秒 | 178テスト（acceptance 65、forbidden 101、cover 11、ランダムウォーク1）、1.35MB。警告50件（cover を作れなかったアクション） |

各ステップの後に状態全体（注文ごとに約30項目、出品、出金、ユーザーの状態）を照合する。期待値は仕様の解釈器が計算する。

## 評価

**楽になる点**
1. **期待値（オラクル）を手で計算しなくてよい。** 手数料や売上、状態遷移の結果を仕様が計算する。人やLLMが期待値を書き間違える余地がない。
2. **定式化で書いたトレースが、そのままテストになる。** Spike 3 で書いた166本が、そのまま178件の実行可能なテストになった。
3. **ランダムウォークによる差分テスト。** 人が書かない操作の組み合わせを、仕様を正解として流せる。
4. **仕様を変えたら再生成できる。** テストの保守が Adapter だけで済む。6言語（vitest、pytest、swift、kotlin、dart、phpunit）に対応しているので、受託案件の技術構成にも合う。

**重い点・制約**
1. **前提として FSL 仕様が必要。** 要件18件の仕様で、エージェント時間が約3時間かかった（Spike 3）。
2. **Adapter の結合が強い。** `observe()` は、実装の状態を仕様の抽象状態（約35項目、小さな円の範囲、bool フラグ、期限を「イベント」として扱う形）に写す必要がある。タイマーは時計を進める処理に、金額は抽象化された値に対応づける。仕様の表現を変えると Adapter も壊れる。
3. **層の粒度の問題（公式の注意）。** 適合性テストは、実装と同じ粒度の層（通常は design 層）から生成すべきとされている。要件層の肯定側テスト（acceptance、cover、ウォーク）は、正当な実装でも誤って失敗しうる。層をまたいで安全なのは forbidden だけ。つまり、design 層の FSL をもう1つ書くか、実装の API を要件のアクションにそろえる必要がある。
4. **性能。** 公式の規模の仕様では、深さ4で生成が終わらなかった。深さ2では、cover を作れたのは61アクション中11件だけ。
5. **範囲。** モデルの外にあるもの（時間の長さ、実際の金額、エラーコード、冪等性など）はテストされない。

**未測定**：Claude が Markdown から直接書くテストと比べて、バグ検出力と工数がどうなるか。
測るには、実装の作成、Adapter の接続、LLM によるテスト作成、バグの注入を行う比較実験（推定3〜4時間）が必要。

## Combへの含意（暫定）

- テスト生成は「FSLを使う理由」になりうる。ただし、FSL仕様と Adapter という重い前提があるので、v0 の中核ではない。
- Comb の IR → FSL のコンパイル経路でも `testgen` は動いた（7.7秒）。IR から FSL を経由してテストを生成する経路は、技術的には成立する。ただし、モニター変数が期待状態に漏れる問題は直す必要がある。
- 本格的な評価は、FSL を opt-in で入れるマイルストーンの入口で行う（比較実験を入口の判定基準にする）。
