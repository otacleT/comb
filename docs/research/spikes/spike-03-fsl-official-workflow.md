# Spike 03：FSL公式ワークフロー準拠の評価（Phase A）

実施日: 2026-10-04〜05 / 成果物は `.spike/spike3/req/`（git 管理外）

## 問い

FSL を公式どおりに使ったとき、静的検証（BMC、帰納法、mutate）は、LLMの読解が見逃す仕様の問題を見つけるか？
公式どおりとは、最新の Agent Skill 4.8.1 と fslc 4.8.1 を使い、`fsl-requirements` ワークフロー（定式化メモ → 人への質問 → 実装 → strict-tags ゲート → verify / induction → mutate → 修正ループ）に従うこと。

## 実験設計

- **入力**：Spike 2 のベース仕様（`spike2/base/spec.md`。REQ-01〜18、D-01〜03）。
- **FSL作成者**：Skill 4.8.1 を読ませ、ワークフローに厳密に従わせたエージェント。Spike 1/2 の成果物は見せていない。
- **PM（仕様オーナー）**：元の会議メモと仕様を持つエージェント。質問に回答し、決定を追加する。
- **比較対象**：Spike 1 の Claude単体レビュー（BL-01〜23。ほぼ同じ仕様に対するもの）。

## 結果

### 工程ごとの発見

| 工程 | 仕様上の問題（人への質問） | 備考 |
|---|---|---|
| 定式化メモ（検証の前） | **23問**（Q-01〜23） | ベースラインの約17件と一致。新規は Q-12（注文後のアカウント制限）、Q-23（D-02 の後始末）など |
| PMの回答 | 新しい決定 **D-04〜D-15**（12件） | |
| strict-tags ゲート / lint | 0 | 全要件の紐付けを機械的に確認できた（網羅性の保証） |
| verify（BMC）の反例 | **0**（反例は1件あったが、モデル化の誤りだった） | `FeeAndProceedsFormula` を常時成り立つものとして書いていた。仕様は「完了時」 |
| induction の CTI（帰納法で出る偽の反例） | **0**（4ラウンド、補助不変条件を17個追加） | すべて到達不能な状態（phantom） |
| mutate で生き残った変異体 | **0**（ただしモデル化の誤り1件：公平性の過剰な仮定） | kill率 0.915（528/577）。生き残り49件は等価31件、スコープ不足7件など |
| エンコード中のエージェント自身の読解 | **3問**（V-01〜03） | V-01/02 はベースラインの BL-10 C/D と同じ。**V-03 は新規**（新しい決定 D-14 と D-01 の相互作用） |

**静的検証（verify、induction、mutate）から出た仕様上の問題は 0件。** これらの道具が見つけたのはすべて、**FSLモデル自体の誤り**だった（9件。トレースのミス、強すぎる不変条件、誤った公平性の仮定など）。

### 静的検証が残したもの（発見以外の価値）

- 不変条件49個と2状態プロパティ16個を、深さの制限なしで証明（注文2件、出品2件、ユーザー3人、¥0..20 の範囲）。
- liveness 5個を有界検証（注文1件、深さ8）。
- 受け入れ65件・禁止101件のトレースがすべて再生できた。シナリオの雛形は177件で、テストの資産になりうる。
- モデルの忠実度が上がった。誤った公平性の仮定（「全員が必ず支払う」）は mutate がなければ見逃していた。

### コスト

- FSL作成エージェントの合計は**約2.9時間・67万トークン**（メモ約20分、Phase 2 約2.6時間。mutate は時間切れで打ち切り）。これとは別に、PMの回答に約7分。
- FSL は約2,000行（127KB）。
- 公式のスコープでは計算が終わらず、次の縮小が必要だった。
  - 金額 ¥0..12000 → ¥0..20
  - 注文 3 → 2
  - 全体モデルの BMC は深さ4まで
  - mutate のカタログ（2,876件）を外部で作り直した
- エージェントが挙げた難所：①検証コストと Skill が想定するスコープの乖離、②帰納法のための補助不変条件づくり、③生き残った変異体の選別（約2/3がノイズ）。

## 結論

- **公式ワークフローに準拠しても、静的検証そのものは、このドメインでLLMの読解を超える仕様上の問題を見つけなかった。**
  発見はすべて、定式化の規律（メモ、網羅表、前提の台帳、エンコード中の読解）から生まれた。Spike 1/2 と同じ構図。
- **FSLワークフローの価値は「規律」と「保証」にある。**
  - 規律：用語集、要件の正規化、網羅表、前提の台帳、質問。これが強いレビューとして働いた。
  - 保証：strict-tags による網羅性、帰納法による証明、mutate によるモデルの健全性。
  - ただし保証の対象は、縮小したスコープのモデル。
- **コストは大きい。** 仕様1本（要件18件）の初回定式化に、エージェント時間で約3時間かかった。変更のたびに回す運用は、現状では重い。
- **注意点**：検証したドメインは1つだけで、仕様はLLMが書いたもの。レビュアーも同じ系統の強いモデル。
  次の2つは未検証：実装との適合性（testgen / replay）と設計層への詳細化（refine）。
