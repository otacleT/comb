# Spike 02：変更時の回帰検出

実施日: 2026-10-04 / コードはすべて使い捨て（`.spike/` は git 管理外）

## 問い

承認済みの仕様に変更（OpenSpec delta）が入ったとき、Claude単体の差分レビューと
IR更新 → 再検証とで、どちらが変更による矛盾や回帰をより確実に見つけられるか？

## 実験設計

- **ベース**：Spike 01 の仕様に、回答 D-01〜D-03 を本文と Decisions 節に反映したもの（`base/spec.md`、630行）。
  対応するIRは Spike 01 の r2 で、58,686状態で全ルールが証明済み、デッドロックなし、シナリオ全通過。
  → 変更後に違反が出れば、それはその変更による回帰。
- **変更**：PM役のエージェントに、現実的な要望5件をもとに delta を書かせた（`changes/<id>/proposal.md`、`delta.md`）。検証の存在は知らせていない。
  1. auto-cancel-unshipped（Ops）
  2. withdraw-cancel-request（CS）
  3. agreed-partial-refund（Product）
  4. proceeds-holding-period（Finance）
  5. instant-cancel-window（Product）
- **Claude単体のレビュー**：変更1件につき独立したエージェント1つ（PRレビューと同じ条件）→ `review/<id>.md`
- **IR更新**：変更1件につき独立したエージェント1つ。ベースIRのコピーに変更を反映。使えるのは lint のみで、検証は回させない → `changes/<id>/ir.yaml`
- **回帰チェック**：`check-change.sh`。1インスタンスの明示的状態探索で全安全ルールを検証し、さらにデッドロックとカバレッジ、シナリオ（ベース分＋新規分）を検査する。違反があれば列挙する。

## 結果

| 変更 | レビューの指摘（high） | Verifierの回帰 | 検証規模・時間 | IRのnotesとレビューの重なり |
|---|---|---|---|---|
| auto-cancel-unshipped | 9件（2） | **0**（証明） | 39,550状態 / 約1分 | 4件（high 1件：リリース時の移行） |
| withdraw-cancel-request | 6件（0） | **0**（証明） | 90,898状態 / 約2分 | 2件 |
| agreed-partial-refund | 9件（1） | **0**（証明） | 229,998状態 / 約15分 | 2件 |
| proceeds-holding-period | 8件（2） | **0**（証明） | 144,174状態 / 約7分 | 3件（high 1件：二重計上） |
| instant-cancel-window | 8件（1） | **0**（証明） | 469,320状態 / 約26分 | 4件（high 1件：配送中の再出品） |
| **合計** | **40件（6）** | **0** | | **約15件（high 3件）** |

5件とも、ベースのシナリオ40件と新しいシナリオがすべて通り、デッドロックもなかった。

### なぜ Verifier は何も見つけなかったか

レビューの指摘40件を分類すると、次のとおり。

1. **IRがモデル化していない次元**：時間の長さや期限の移動（auto-cancel の CR-01、agreed の CR-06）、リリース時の移行、エラーコードの優先順位、物理的な荷物の所在、評価やペナルティなどのインセンティブ、複数注文の直列化。過半数がこれ。
2. **IR更新エージェントが、あいまいな箇所を安全な解釈でエンコードし、notes に書き残したもの**。代表例が holding-period の CR-02（熟成済みの売上が pending に残ったまま出金されて二重計上）。エージェントは「スケジュールされた移動は、まだ pending にある分だけを動かす」とエンコードし、そのことを gap として notes に書いた。そのため、Verifierには矛盾として見えない。
3. **ベースのIRが表現していないお金の流れ**：チャージバックで買い手に戻る額（auto-cancel の CR-03、agreed の CR-02）。Spike 01 の r2b の教訓を、ベースIRに入れていなかった。

## 分かったこと

1. **変更レビューでも、Verifierの発見力の上乗せは確認できなかった。** 5件の変更すべてで回帰は0件、証明済み。一方で、Claude単体のレビューは40件（high 6件）を指摘した。
2. **LLMにIRを書かせる工程自体が、強いレビューになっている。** 「仕様を厳密な振る舞いモデルに落とし込め、落とせないところは notes に書け」という強制が、レビューの指摘の約4割（high 3件を含む）を独立に拾った。レビューにない指摘もあった（ウィンドウ内に保留が入ると一度も使えずに失効する、出荷期限後に取り下げが可能になる）。
3. **IRを書くLLMは、矛盾をモデルに入れずに notes へ逃がす。** 指示は「忠実にエンコードせよ」だったが、実際の仕様はあいまいで、エージェントは整合的な解釈を選び、問題は notes に書く。これは良い振る舞いだが、結果として Verifier が働く余地がなくなる。
4. **検証のコストは、機能を足すたびに増える。** 状態数は 58k → 230k に増え、時間も 30秒 → 15分と伸びた。グローバルなカウンタを足した instant-cancel は469k状態で26分かかった。変更ごとに検証を回す運用には、抽象化の規律が要る。
5. **`fslc diff` は使えなかった。** アクションや状態の名前が変わると `unknown` を返す。変更は通常アクションを追加するので、Combの変更影響分析には使えない（mapping を書く必要がある）。

## Spike 01 と 02 を通した結論

| 価値 | 実証できたか |
|---|---|
| Verifier が LLM の見逃す問題を見つける | ✗（初回レビューでも変更レビューでも、根本原因レベルでは0件） |
| Verifier が「回答後／変更後の仕様は、モデル化したルールをすべて満たす」と証明する | ○（ただし IR の忠実度に依存。誤った安心感のリスクがある） |
| LLMレビュー（構造化された出力：手順・重要度・確信度・質問と選択肢） | ◎（初回23件、変更40件。質が高い） |
| 振る舞いモデルの抽出を「レビューの観点」として使う | ○（初回6件、変更で約15件。独自の指摘もある） |
| 発見事項 → 回答可能な質問 → Decision → 仕様への反映 | ◎（質問の質が高く、D-01〜03 をきれいに反映できた） |
| FSL をバックエンドとして使う技術的な実現性 | ◎（決定的コンパイル、JSON、要件ID、速度。障害なし） |

## Combへの示唆（たたき台）

- **v0 の中核は「収束ループ」にする。** 多観点の LLM レビュー → 質問 → 人の決定（Decision）→ 仕様の更新、のループ。形式検証は v0 の中核にしない。
- **振る舞いモデルの抽出は、v0 のレビュー観点の1つとして残す。** モデル検査器なしで、notes だけでも価値がある。IR形式は将来の検証にもそのまま使える。
- **FSLによる検証は、後のマイルストーンで opt-in にする**（`comb verify --deep` など）。
  - 対象：お金や状態が致命的なドメインで、「証明」が欲しいとき。
  - 再検討するきっかけ：LLM レビューが見逃した不具合が実際に発生したとき。または、ドメイン不変条件パック（お金の保存則、保留中の凍結、一度だけの実行など）と忠実エンコードの規約が成熟したとき。
- **未検証の仮説**：FSL の testgen / replay / conformance による「仕様と実装の乖離の検出」。発見ではなく適合性という、別の価値軸。
