# Spike 01〜04 の要約

2026-10-04〜05 に、Comb の中核の前提「形式検証（FSL）が仕様の矛盾発見の差別化になる」を4回の spike で検証した。
詳細は `spikes/` の各レポートを参照。

## 共通の題材

C2C マーケットプレイスの注文ライフサイクル。決済、発送、キャンセル、Dispute、返品、返金、チャージバック、出金を含む。

- 仕様：要件18件、シナリオ52件、624行。PM役のエージェントが会議メモから書いた。
- 比較対象：Claude単体のレビュー（ベースライン）。工程ごとに独立したエージェントを使い、互いの成果物は見せていない。

## 結果

| Spike | 問い | 結果 |
|---|---|---|
| [01](spikes/spike-01-verification-loop.md) | Markdown → IR → FSL → 反例 → 質問 のループは、LLMレビューが見逃す問題を見つけるか | 根本原因レベルでは、ベースラインに対する上乗せは **0件**（ベースライン23件、Verifier 3件はすべて重複）。ただし、回答を反映した後の仕様が全ルールを満たすことは証明できた。お金の流れを1つモデル化し忘れただけで、誤った「証明済み」が出た |
| [02](spikes/spike-02-change-regression.md) | 変更（delta）時の回帰検出は、LLMの差分レビューより確実か | 変更5件で、Verifier の回帰は **0件**、LLMレビューは40件（high 6件）。IR を書くエージェントの notes が、指摘の約4割を独立に拾った |
| [03](spikes/spike-03-fsl-official-workflow.md) | FSL を公式どおり（Skill 4.8.1 の `fsl-requirements` ワークフロー）に使えばどうか | 静的検証（verify、induction、mutate）から出た仕様上の問題は **0件**。発見は定式化メモ（23問、ベースラインの約17件と重複）とエンコード中の読解（3問）に集中した。約2.9時間のエージェント時間がかかり、スコープも大きく縮める必要があった |
| [04](spikes/spike-04-fsl-testgen.md) | FSL でテスト作成は楽になるか | `testgen` で、期待値を自動計算する適合性テストを生成できた（178件、6言語に対応）。ただし、FSL 仕様、Adapter、層の粒度、性能という重い前提がある。LLMが書くテストとの比較は未測定 |

## 結論（Comb の設計に反映したこと）

1. **形式検証は v0 の中核にしない。** 発見力の上乗せが確認できず、コストは大きい。後のマイルストーンで opt-in にする。（`DECISIONS.md` D-004）
2. **価値があったのは「構造化されたレビュー」と「定式化の規律」。** 用語集、要件の正規化、網羅表、前提の台帳、状態×イベントを、レビューの観点として組み込む。（D-005）
3. **指摘を、答えられる質問にして、Decision → 仕様へ反映するループは質が高かった。** これを Comb の中心に置く。（D-003）
4. **「証明済み」は、モデル化の範囲を開示しない限り誤った安心感になる。** 将来、検証を入れるときも、カバレッジの開示を必須にする。（D-004）
5. **振る舞いモデル（IR）を Markdown に埋め込まない。** 規模が大きく、人が読む表にならない。（D-006）

## 注意（一般化の限界）

- 題材のドメインは1つだけ。仕様はLLMが書いたもので、人の書く仕様より整っている。
- レビュアーは同じ系統の強いモデル。
- 未検証のもの：実装との適合性（`testgen` / `replay`）、design 層への詳細化（`refine`）、人が書いた雑な仕様での比較。
