# v0.1 設計：Document Profiles（solo）

関連：[DESIGN §9.1](../DESIGN.md) / [V0_SCOPE](../V0_SCOPE.md) / [DECISIONS](../DECISIONS.md) / [PRODUCT_PRINCIPLES 原則10](../PRODUCT_PRINCIPLES.md)

## 1. 目的

個人開発者が、アイデアを Comb の仕様に落とし込んだ後に読む、プロダクト仕様のドキュメントを作る。受託開発の要件定義書ほど厳密である必要はない。画面や機能がどう振る舞うかが一通り整理されていて、spec.md より読みやすい入口になればよい。

## 2. 決定済みの前提（2026-10-06〜08、ユーザーの回答）

| 項目 | 決定 |
|---|---|
| 読者と用途 | 個人開発者本人（と協力者）が、プロダクトの仕様を一通り把握するために読む |
| 情報源 | 正本（`comb/specs/`、`comb/decisions.md`、archive 済みの change）からだけ作る。ドキュメント独自の情報は持たない。足りない情報は「仕様に未記載」として挙げ、`/comb:propose` で仕様に足す |
| 作り方 | エージェントがプロダクトの視点で書き、CLI が引用と生成元のハッシュで縛る（方式 B。決定的な描画（A）や併用（C）は採らない） |
| 構成 | 6本：product、features、screens、flows、decisions、open-questions |

## 3. 生成するドキュメント（solo profile）

| ファイル | 内容 | 生成元（`sources`） |
|---|---|---|
| `product.md` | 何のためのプロダクトか、誰向けか、全体の地図（capability と主な機能の一覧） | `config`、`specs` |
| `features.md` | 機能ごとの振る舞い。何ができて、どんな条件で、どうなるか（シナリオを受け入れ条件の例として使う） | `specs` |
| `screens.md` | 画面ごとの振る舞い。仕様に画面の記述がなければ、「仕様に未記載」の一覧だけになる | `specs` |
| `flows.md` | 主な利用の流れと、状態の移り変わり | `specs` |
| `decisions.md` | 何をなぜそう決めたか。置き換えられた決定は履歴として示す | `decisions` |
| `open-questions.md` | まだ決めていないこと、保留して受け入れたリスク（D-019 で保留した high を含む） | `open-questions` |

- 書き出し先は `<documents.dir>/<ファイル>`（既定は `docs/`）。本文は `config.yaml` の `language` で書く。構造のキーワード（見出しの `Gaps` など）は英語で固定する（D-013）。
- ドキュメントは正本だけを映す。作業中の change は含めない。
- 分量は必要最小限にする。要件の全文は写さず、要約して ID でリンクする。
- architecture（どう作るか）は正本にないので含めない。verification は、features.md のシナリオ（受け入れ条件）に含める。

## 4. 生成元とハッシュ

`sources` に指定できる値と、それぞれの内容：

| 値 | 内容 |
|---|---|
| `config` | `comb/config.yaml` の `context` |
| `specs` | すべての正本の仕様（`comb/specs/*/spec.md`） |
| `decisions` | `comb/decisions.md` |
| `open-questions` | archive 済みの change の `questions.md`（`comb/changes/archive/*/questions.md`） |

- ドキュメントごとの生成元ハッシュは、宣言された生成元のファイル（パスと LF に正規化した内容）を、パスのコードポイント順に連結した sha256 の先頭16桁（`sha256:<16桁>`）。`config` は context の文字列を使う。
- ハッシュは CLI だけが書く（`comb docs stamp`）。エージェントは書かない。

## 5. 生成物の印とユーザーのファイル

- 生成物の1行目は、次のどちらか。
  - エージェントが書いた直後：`<!-- generated by comb for sha256:<16桁> -->`。ハッシュは、`comb instructions docs` が出力ごとに渡す、書いた時点の生成元ハッシュ（`marker`）。
  - stamp の後：`<!-- generated by comb from sha256:<16桁>; edit the specs, not this file -->`
- テンプレートの1行目は `<!-- generated by comb -->` で、エージェントはそれを `marker` に置き換える。
- 1行目が `<!-- generated by comb` で始まるファイルを生成物とみなす。書き出し先に、この印のない同名ファイルがあれば、それはユーザーのファイルである。エージェントは上書きせずユーザーに確認し、CLI は `DOC_USER_OWNED` を報告する。

## 6. 規則（profile の SKILL.md としてエージェントに渡す）

1. 振る舞いについての記述には、必ず根拠の ID を付ける。
   - 要件：`REQ-<PREFIX>-<NNN>`
   - 決定：`D-<NNN>`（恒久ID）
   - 保留中の質問：`<change-id>#Q-<n>`（archive フォルダ名から日付を除いた change ID。例：`add-subscription-billing#Q-3`。文中の「Q-3」などと区別するため `#` でつなぐ）
   - プロジェクトの文脈（`config.yaml` の context）：`config:context`
2. 正本にないことは書かない。テンプレートが求めるのに仕様にない情報は、各ドキュメント末尾の `## Gaps` に挙げる。Gaps が次の `/comb:propose` の材料になる。
3. 要件の全文は写さない。読者の視点で組み替えて要約し、ID でリンクする。
4. 書き出し先に印のないファイルがあれば、書かずにユーザーに確認する。
5. 書いたファイルの1行目は、`comb instructions docs` が渡す `marker`（`<!-- generated by comb for sha256:… -->`）にし、最後に `comb docs stamp` を実行する。

## 7. CLI

| コマンド | 内容 |
|---|---|
| `comb docs [--json]` | ドキュメントごとの状態（`missing` / `stale` / `done` / `user-owned`）と、引用・網羅性の診断を表示する。error があれば exit 1（CI やコミット前の確認にもそのまま使う） |
| `comb docs stamp [--json]` | 1行目の `for` のハッシュが現在の生成元ハッシュと一致する生成物だけを、stamp 後のヘッダに書き換える。書いた後に正本が変わったもの、`for` のない印、古いハッシュを持つもの、印のないファイル、存在しないファイルには触れない。古い正本から書いたものを done に見せかけることを防ぐため |
| `comb instructions docs [--json]` | profile の出力一覧（パス、テンプレート、読者、生成元、現在の状態）、規則（SKILL.md）、指示文、読むべきファイル、言語を返す。change に属さないので `--change` は要らない（ほかの artifact では引き続き必須） |

`comb docs --json` の `data`：

```json
{ "profile": "solo", "dir": "docs",
  "outputs": [{ "id": "features", "path": "docs/features.md", "state": "stale",
                "sourceHash": "sha256:…", "recordedHash": "sha256:…" }],
  "uncovered": ["REQ-SUB-014"] }
```

## 8. 検査（`comb docs`）

| コード | 重さ | 内容 |
|---|---|---|
| `DOC_MISSING` | error | 書き出し先のファイルがない |
| `DOC_STALE` | error | 記録された生成元ハッシュが、現在の正本と違う。または未記録（stamp 前） |
| `DOC_USER_OWNED` | error | 書き出し先に、印のないファイルがある |
| `REF_UNKNOWN_REQ` | error | 存在しない、または削除済み（retired）の要件を引用している |
| `REF_UNKNOWN_DECISION` | error | `comb/decisions.md` にない Decision を引用している |
| `REF_UNKNOWN_QUESTION` | error | archive にない change、またはその change にない質問を引用している |
| `REF_UNKNOWN_SECTION` | error | 正本の capability の、存在しない節を引用している（F4 で追加） |
| `REF_EMPTY_CONTEXT` | error | `config:context` を引用しているが、`config.yaml` の context が空 |
| `DOC_UNCITED_SECTION` | warning | `##` または `###` の節（見出しを含む。`## Gaps` とその配下を除く）に、引用が1つもない |
| `DOC_UNCOVERED` | warning | 正本の要件のうち、どのドキュメントにも引用されていないものがある |
| `DOC_CITES_SUPERSEDED` | warning | decisions を生成元に持たないドキュメントが、置き換えられた Decision を引用している（v0.1 の後に追加） |

- 引用の抽出：要件 `\bREQ-[A-Z][A-Z0-9]*-\d{3,}\b`、Decision `\bD-\d{3,}\b`、質問 `\b<change-id>#Q-\d+\b`、文脈 `config:context`（節の引用として数えるが、検査する対象はない）、正本の節 `<capability>#<見出し>`（F4 で追加。`#` の前が正本の capability 名のときだけ引用とみなし、見出しは大文字・小文字を区別しない。パス、ファイル名、URL の一部は除く。D-023）。コードブロックの中も数える（例として ID を書く場合も、存在する ID であるべきため）。
- 引用と節の検査は、生成物（印のあるファイル）だけが対象。
- 1文ごとの引用の有無は判定しない。節単位の引用の有無と、全要件の網羅で縛る。

## 9. profile の形式

組み込みの solo は、パッケージ内の `templates/profiles/solo/` に置く。

```
templates/profiles/solo/
├── profile.yaml
├── SKILL.md              # 書き方の規律（§6）、読者、用語。Claude Code の Skill としてはインストールしない
└── templates/
    ├── product.md        # 見出しの骨組みと、各節に書くことの説明
    ├── features.md
    ├── screens.md
    ├── flows.md
    ├── decisions.md
    └── open-questions.md
```

`profile.yaml`：

```yaml
id: solo
type: comb.document-profile
version: 1
outputs:
  - id: product
    path: product.md
    template: templates/product.md
    audience: you and new collaborators
    sources: [config, specs]
  # features / screens / flows / decisions / open-questions も同じ形
```

- profile の読み込みは、ディレクトリのパスを受け取る汎用の関数にする。v0.2 でユーザー定義の profile（`comb/profiles/<name>/`）と client-work を足せるようにするため。
- `type` が `comb.document-profile` でない、`version` が 1 でない、`sources` に未知の値がある、`template` が存在しない、のいずれかなら `CONFIG_INVALID`。

## 10. 設定

`comb/config.yaml` に `documents` を追加する。省略時は既定値を使う。

```yaml
documents:
  profile: solo   # v0.1 で選べるのは solo だけ
  dir: docs       # プロジェクトのルートからの相対パス
```

- `profile` が `solo` 以外なら `CONFIG_INVALID`（「v0.1 で使える profile は solo だけ」）。
- `dir` が絶対パス、`..` を含む、または `comb/` の中を指す場合は `CONFIG_INVALID`。

## 11. Skill

- `templates/skills/docs.md` から `/comb:docs` と `comb-docs` の Skill を生成する。既存のプロジェクトにも `comb update` で入る。手順：
  1. `comb docs --json`
  2. `comb instructions docs --json`
  3. 状態が `missing` と `stale` のドキュメントだけを書く
  4. `comb docs stamp`
  5. `comb docs --json` で error がなくなるまで直す
  6. 更新したドキュメントと Gaps を報告する
- archive の Skill に手順を足す：archive が成功したら `comb docs --json` を実行し、`stale` のドキュメントがあれば `/comb:docs` を勧める。自動では再生成しない（LLM の費用がかかるため）。

## 12. 範囲外（v0.1 では作らない）

- ユーザー定義の profile、client-work（v0.2）
- MkDocs、Docusaurus などの表示層との連携
- 1文単位の引用の検査、引用の意味的な正しさの判定
- 自動での再生成、`comb status` への表示

## 13. 確認方法

**ユニットテスト（vitest）**
- profile の読み込みと検証
- 生成元ハッシュ（生成元ごとに、関係のない変更では変わらないこと）
- 引用の抽出と検査（存在しない ID、削除済みの ID、archive にない質問）
- 引用のない節（`## Gaps` を除く）、網羅性
- 印の判定、stamp（ハッシュのない生成物だけに書く。stale なものと印のないファイルには触れない）
- `instructions docs` が `--change` なしで動き、ほかの artifact では `--change` が必須のままであること
- 設定の検証

**体験の確認 E7（v0.1 の完了条件）**
1. ベンチマークの subscription-billing（16要件）を、新しいプロジェクトで正本に archive する（`--yes`）。
2. `/comb:docs` を実行する。合格条件：
   - `comb docs` が error なしで通り、`DOC_UNCOVERED` が0件。
   - 各ドキュメントの `## Gaps` が、実際に仕様にない点を挙げている（例：画面の記述）。
   - 記述を5件抜き取り、引用先の要件に裏付けがあることを確かめる。
3. 手で作った小さな change（要件1つの MODIFIED）を archive する。
   - `comb docs` が specs を生成元とするドキュメントだけを `stale` にし、decisions.md と open-questions.md は `done` のままであること。
   - `/comb:docs` を再び実行し、stale のものだけが作り直されて、検査が通ること。
4. 実際の LLM の費用は $5〜10 程度の見込み。

## 15. リスク

| リスク | 対策 |
|---|---|
| エージェントが正本にないことを書く | 節単位の引用の検査、網羅性、`## Gaps` への誘導。E7 で抜き取り確認する |
| 仕様が大きいと、1回の生成の費用がかさむ | 生成元をドキュメントごとに宣言し、stale のものだけを作り直す |
| `docs/` に既存のドキュメントがある | 印のないファイルは上書きしない。`documents.dir` で書き出し先を変えられる |
| 生成のたびに文面が変わる | 正本が変わらなければ stale にならないので、作り直すのは正本が変わったときだけ |
